## 0. 早上问了什么：问题清单与结论速查

| # | 问题 | 核心结论（一句话） | 对应章节 |
|---|---|---|---|
| 1 | 为什么函数在 main 外面调用后会被销毁，底层发生了什么 | 全局域根本不能写函数调用语句；你看到的现象其实是**全局对象在 main 前构造、main 返回后析构** | 第 1 章 |
| 2 | 全局变量和局部变量初始化的区别 | 全局：加载期就位 + main 前动态初始化；局部：**执行到那一行才初始化**，不写初值就是垃圾值 | 第 2 章 |

| 4 | 局部变量和全局变量的存储位置分别在哪里 | 局部在**栈**；全局/static 在**静态区**（`.data` / `.bss`） | 第 4 章 |
| 5 | 静态区是什么 | 存放「静态存储期」数据的内存区域，由 `.data` + `.bss`（+`.rodata`）组成，进程不退出就不回收 | 第 5 章 |
| 6 | 块级作用域是什么 | 一对 `{}` 划出的范围，管**名字可见性 + 自动变量的生命周期**，但改不了变量存在哪个区 | 第 6 章 |

**最容易搞混的一条主线**：
> 存储位置（内存放哪） ≠ 存储期（活多久） ≠ 作用域（名字在哪能看见） ≠ 链接属性（能不能跨文件用）
> 这四件事是**相互独立**的四个维度，`static` 这个关键字恰好同时改了其中三个，所以特别容易混。

## 1. 问题一：函数在 main 外面调用，到底发生了什么

### 1.1 先分清两种完全不同的现象

你说「在 main 外面调用后被销毁」，实际上可能撞上了两件完全不同的事：

| 现象 | 本质 | 是否合法 |
|---|---|---|
| 在全局域直接写 `foo();` | 语法错误，**编译不过** | 非法 |
| 定义全局变量 `A a;`，看到构造/析构在 main 前后跑 | 全局对象的**静态初始化**（CRT 自动调用） | 合法，是语言特性 |
| 定义 `static` 局部变量，看到它在函数里只初始化一次、程序结束才析构 | `static` 局部变量 | 合法 |

### 1.2 全局域为什么不能写执行语句

C/C++ 的语法规定：**文件作用域（全局域）只允许「声明/定义」，不允许「语句」**。

函数调用、`if`、`for`、赋值表达式语句，这些都属于「可执行语句」，必须放在函数体里面。

**实测**：

```cpp
// t4.cpp
#include <cstdio>
void foo(){}
foo();              // ← 全局域裸写函数调用
int main(){ return 0; }
```

```
t4.cpp:3:6: error: expected constructor, destructor, or type conversion before ';' token
    3 | foo();
      |      ^
```

编译器在全局域看到 `foo();`，它只会去猜「你是不是想定义一个叫 `foo` 的变量」，然后失败。
所以「在 main 外面调用函数」这件事，**在语法层面根本不存在**。你能观察到执行代码，只有一条途径：**全局对象的初始化**。

### 1.3 真正在 main 之前跑的是什么：全局对象的构造

```cpp
struct A {
    const char* name;
    A(const char* n) : name(n) { printf("[%s] ctor\n", name); }
    ~A() { printf("[%s] dtor\n", name); }
};

A global("global");     // ← 这行的构造函数，在 main 之前自动执行

int main() {
    printf("=== enter main ===\n");
    return 0;
}
```

**实测输出**：

```
[global] ctor          ← main 之前
=== enter main ===
[global] dtor          ← main 返回之后
```

关键点：**对象的内存从进程加载那一刻就存在了，构造函数只是「往这块已存在的内存里填初值」**。
所以不是「调用完构造就销毁」，而是**进程快结束时才跑析构**。

### 1.4 底层流程：程序不是直接跳进 main 的

```
① OS 加载 ELF，建立虚拟地址空间
   └─ 映射 .text / .rodata / .data / .bss，建立栈、堆区
② 入口跳 _start（ld 给的，不是 main）——Windows 下是 _CRTStartup
   └─ 设栈、清寄存器、初始化 CRT
③ CRT 遍历 .init_array（旧名字 .ctors）
   └─ 逐个调用全局/命名空间作用域对象的构造函数
④ 调用 main(argc, argv)
⑤ main return → 回到 CRT
⑥ CRT 遍历 .fini_array（旧名字 .dtors）
   └─ **逆序**调用全局对象的析构函数 + atexit 注册的回调
⑦ _exit 系统调用 → OS 回收整个进程地址空间
```

**为什么是逆序？** 因为后构造的对象可能依赖先构造的对象，析构必须反着来（栈式语义）。

### 1.5 实测：完整生命周期对照

```cpp
// t1.cpp
A global("global");

void test() {
    A local("local in test");        // 栈对象
    static A stat("static local");   // 静态区对象
    printf("inside test\n");
}

int main() {
    printf("=== enter main ===\n");
    test();
    test();
    printf("=== leave main ===\n");
    return 0;
}
```

**实测输出（原样复制）**：

```
[global] ctor
=== enter main ===
[local in test] ctor
[static local] ctor
inside test
[local in test] dtor
[local in test] ctor
inside test
[local in test] dtor
=== leave main ===
[static local] dtor
[global] dtor
```

四条规律，一眼可见：

1. `global` 的构造在所有事情之前 → 说明它在 `.init_array` 里；
2. `local` 每次进函数构造、出函数立刻析构 → 栈对象，作用域驱动；
3. `static local` **第一次进函数才构造**（注意它打印在 `enter main` 之后）→ 它**不在 `.init_array`**，靠运行时的一次性保护机制；
4. 最后 `static local` 先析构、`global` 后析构 → **逆序销毁**。

### 1.6 必须建立的三个认知校正

- ❌「函数调用完就被销毁了」 → ✅ 栈上的自动对象确实出作用域就销毁，但**全局对象不参与这个规则**；
- ❌「全局变量就是先执行一遍它的初始化代码，然后没了」 → ✅ 内存一直在，直到进程退出；
- ❌「main 是程序入口」 → ✅ main 只是 CRT 调用的**用户代码入口**，真正的入口是 `_start`。

## 2. 问题二：全局变量 vs 局部变量的初始化区别

### 2.1 一句话总纲

> **全局（含 static）：内存提前就位，初始化分「内核静态填值」和「CRT 运行期构造」两档；
> 局部（普通）：函数执行到这一行，才在栈上分配 + 初始化。**

### 2.2 默认值差异（最容易出事的地方）

```c
int g;              // 全局，不写初值
void f() { int a; } // 局部，不写初值
```

| | 全局 `g` | 局部 `a` |
|---|---|---|
| 落在哪个段 | `.bss` | 栈 |
| 默认值 | **一定是 0**（指针是 NULL） | **不确定，是栈上残留的旧数据** |
| 谁负责 | OS 加载时把整片 `.bss` 清零 | 没人负责，栈指针挪一下而已 |
| 读它的后果 | 安全 | **未定义行为（UB）** |

**实测**（t3.cpp 中的 `g_zero`、`g_static_zero`）：

```
g_zero   =0 addr=0x55fde9926020
g_static =0 addr=0x55fde9926024
```

两个都没写初值，值都是 0 —— 这就是 `.bss` 被内核清零的证据。

### 2.3 初始化时机：三档，不是两档

| 档位 | 触发时间 | 典型代码 | 由谁完成 |
|---|---|---|---|
| ① 编译期常量初始化 | **编译时**就写进文件 | `int g = 10;` `const int c = 5;` | 编译器写进 `.data` |
| ② 加载期零初始化 | 进程加载时 | `int g;` `static int s;` | 内核/加载器批量清零 `.bss` |
| ③ 运行期动态初始化 | **main 之前**（全局）/ **第一次执行到**（static 局部） | `int g = rand();` `A obj;` | CRT 走 `.init_array` |

> 判断标准：初值能不能在**编译期算出来**。能 → ①②；必须调函数/读运行时状态 → ③。

**实测**（t2.cpp）：

```cpp
int func() { printf("run func\n"); return 1; }
int g = func();                       // 全局动态初始化

void test() {
    int a = func();                   // 局部，每次进函数都跑
    static int s = func();            // static 局部，只跑第一次
}

int main() {
    printf("main start\n");
    test(); test();
}
```

**实测输出**：

```
run func        ← ① 全局 g 的初始化，在 main 之前
main start
run func        ← ② 第一次 test()：局部 a 初始化
run func        ← ③ 第一次 test()：static s 初始化（仅此一次）
run func        ← ④ 第二次 test()：局部 a 又要初始化一次
```

> ⚠️ 这里有个**自我纠错**：我在对话中口算时曾说输出 3 行 `run func`，实测是 **4 行**。
> 因为局部 `a` 被初始化了**两次**（`test()` 调了两次），而 `s` 只有一次。
> 这个多出来的一次，恰好就是「局部 vs static 局部」的核心差别，值得单独记住。

### 2.4 指令层面的差别（为什么全局不花运行时开销）

**全局 `int g = 10;`**
```
编译器直接把 10 写进 .data 段的文件内容里。
程序加载时，OS 把这段文件内容 mmap/copy 到内存。运行时零指令。
```

**局部 `int a = 10;`**（`-O0` 真实汇编形态）
```asm
movl    $10, -4(%rbp)     ; 每次进函数都要执行这条
```
**所以：函数被调用 1 万次，这条 mov 就跑 1 万次。全局变量则一次都不用。**

**全局对象 `A g;`** → 编译器生成一个初始化函数，把它的地址塞进 `.init_array`；
**局部对象 `A a;`** → 函数体内直接生成 `call 构造函数` + 退出时 `call 析构函数`。

### 2.5 static 局部变量：最特殊的一类

```cpp
void f() {
    static A x;      // 或 static int s = func();
}
```

| 维度 | 表现 |
|---|---|
| 内存位置 | **静态区**（`.data` / `.bss`），不在栈 |
| 构造时机 | **第一次执行到这一行**，不是 main 之前 |
| 之后的行为 | 再也不初始化，值一直保留 |
| 线程安全 | C++11 起由编译器保证「只初始化一次」（magic statics，用 `__cxa_guard_acquire` 保护变量） |
| 析构时机 | main 返回后，走 `.fini_array` |
| 作用域 | 仅函数（或块）内部 |

**实测证据**：t1 里 `[static local] ctor` 打印在 `=== enter main ===` 之后 —— 证明它**不在** `.init_array`。
这是最容易说错的一点：很多人以为「static 的都在 main 前构造」，**只有全局/命名空间作用域的才是，static 局部不是**。

### 2.6 跨文件初始化顺序灾难（Static Initialization Order Fiasco）

```
同一编译单元（同一个 .cpp）内：按定义顺序初始化，确定。
跨编译单元（不同 .cpp）：标准不规定顺序，链接器实际排布决定，**不要依赖**。
```

**经典踩坑**：

```cpp
// a.cpp
extern int x;
int y = x + 1;        // ❌ 若 x 还没构造完成，读到的是 0 或垃圾

// b.cpp
int x = 42;
```

正确做法：改用**函数内 static 局部**（C++11 保证首次调用时安全初始化）：

```cpp
int& X() { static int x = 42; return x; }   // 首次访问才初始化，天然规避顺序问题
```

## 3. 问题三：生命周期到底是什么

### 3.1 生命周期 = 「从哪一刻起合法存在，到哪一刻起失效」

| 变量类型 | 生命周期起点 | 生命周期终点 | 存储期术语 |
|---|---|---|---|
| 普通局部变量（自动变量） | 执行到定义语句那一刻 | 离开所在 `{}` 代码块 | 自动存储期 automatic |
| `static` 局部变量 | 内存：进程加载；**初始化**：第一次执行到定义行 | 进程结束（C++ 跑完析构） | 静态存储期 static |
| 全局变量 | 进程加载完成 | 进程结束（C++ 跑完析构） | 静态存储期 static |
| `static` 全局变量 | 同上，只是名字仅限本文件 | 同上 | 静态存储期 static |
| 动态分配（`malloc`/`new`） | 调用成功返回那一刻 | **手动 `free`/`delete`** | 动态存储期 dynamic |
| 函数形参 / 函数内临时对象 | 进入函数 | 函数返回 | 自动存储期 |

### 3.2 三个高频误解

**误解 A：「离开作用域，内存就被清零了」**

```c
void f() { int a = 123; }     // a 所在那 4 字节，值是 123
void g() { int b; }            // 如果 g 复用同一块栈，b 里很可能还是 123
```

真相：出作用域只是**栈指针回退**（`mov rsp` 往回挪），**内存内容一个字都没动**。
所以访问已失效的局部变量，往往真的能读到旧值——但这仍然是 UB，编译器优化随时会把它变成别的东西。

**实测（t3.cpp 栈地址）**：
```
stack_var=1 addr=0x7ffe5beedb04
```
高地址 `0x7ffe...` 是典型栈区间（每跑一次地址还会变，有 ASLR）。

**误解 B：「生命周期结束了，变量就不存在了」**

从语言抽象机看，对象确实「不存在了」；从物理内存看，那块字节还在，只是不再归你。
这就是 **悬垂指针（dangling pointer）** 的来源：

```c
int* bad() { int a = 10; return &a; }   // ❌ 返回局部变量地址，UB
```

**误解 C：「static 局部活到 main 结束」**

准确说法：**一直活到进程结束**。main 返回之后还有一段 `.fini_array` 要走，那时它的析构才发生。

### 3.3 三个名词的严格区分（强烈建议背下来）

| 名词 | 回答什么问题 | 取值 |
|---|---|---|
| 作用域 scope | 名字在**源码的哪个区域**可见 | 块 / 函数 / 文件 / 全局 / 命名空间 |
| 存储期 storage duration | 内存在**运行时活多久** | 自动 / 静态 / 动态 / 线程 |
| 链接属性 linkage | 名字能否**跨编译单元**使用 | 外部 / 内部（`static`）/ 无 |

`static` 关键字出现在不同位置的语义**完全不同**，这是 C 语言最大的坑之一（见第 7 章第 1 条）。

## 4. 问题四：存储位置分别在哪里

### 4.1 进程虚拟地址空间全景（x86-64 Linux 布局）

```
高地址  0x7fff_ffff_ffff
 ┌─────────────────────────────┐
 │  命令行参数 / 环境变量 envp   │
 ├─────────────────────────────┤
 │           栈 stack           │  ← 局部变量、函数帧，向低地址生长
 │             ↓                │
 │                              │
 │             ↑                │
 │           堆 heap            │  ← malloc / new，向高地址生长
 ├─────────────────────────────┤
 │  .bss   （未初始化，NOBITS）  │  ← 加载时整片清零
 ├─────────────────────────────┤
 │  .data  （已初始化，可读写）  │  ← 从文件原样拷贝
 ├─────────────────────────────┤
 │  .rodata（只读常量、字符串）  │
 ├─────────────────────────────┤
 │  .text  （机器码）            │
 ├─────────────────────────────┤
 │  ELF 头 / 段表 / 动态链接信息 │
 └─────────────────────────────┘
低地址  0x0000_0000_0000_0000
```

### 4.2 实测：地址分布 = 位置的铁证

```
g_init    =66 addr=0x55fde9926010      ← 全局有初值，.data
g_zero    =0  addr=0x55fde9926020      ← 全局无初值，.bss
g_static  =0  addr=0x55fde9926024      ← static 全局无初值，.bss
inner     =8  addr=0x55fde9926018      ← 块内 static，.data
s_in_block    addr=0x55fde9926014      ← 函数内 static，.data
stack_var =1  addr=0x7ffe5beedb04      ← 普通局部，栈（高地址 0x7ffe...）
```

读法：
- `0x55fd_xxxxxxxx` 这一段是 **PIE 基址上的静态区**，几个变量地址相邻（都是 `...6010`~`...6024`），说明它们**挤在同一个段里**；
- `0x7ffe_xxxxxxxx` 是 **栈区**，和静态区差了十万八千里；
- `inner` 两次调用地址都是 `...6018`，`s_in_block` 都是 `...6014` → **static 局部内存地址恒定**，不在栈上。

### 4.3 实测：`nm` 的符号类型字母（最硬的一条证据）

```
0000000000004010 D g_init              ← D = 已初始化数据段 .data
0000000000004020 B g_zero              ← B = 未初始化数据段 .bss
0000000000004024 b g_static_zero       ← b = 本地 .bss（static，小写=局部链接）
0000000000004014 d f()::s_in_block     ← d = 本地 .data（函数内 static）
0000000000004018 d f()::inner          ← d = 本地 .data（块内 static）
```

记忆规律：
- **大写字母 = 全局符号（外部链接）**：`D`(data) / `B`(bss) / `T`(text) / `R`(rodata)
- **小写字母 = 本地符号（static，内部链接）**：`d` / `b` / `t` / `r`

看一个变量的符号字母，就能同时读出「它在哪个段」和「它有没有 static 链接」。

### 4.4 实测：`size` 与段表

```
   text    data     bss     dec     hex  filename
   1925     620      12    2557     9fd  t3
```

`.bss` 只有 12 字节（= 8 字节的 `g_zero`？不，是本节里所有未初始化静态变量总和），`.data` 620 字节 —— 注意程序里真正写的变量才几个字节，剩下是 C++ 运行时自带的东西。

```
[16] .text     PROGBITS  0000000000001080
[18] .rodata   PROGBITS  0000000000002000
[25] .data     PROGBITS  0000000000004000    ← 有文件内容（PROGBITS）
[26] .bss      NOBITS    000000000000401c    ← 无文件内容（NOBITS）
```

**`NOBITS` 三个字就是「`.bss` 不占磁盘空间」的官方证据**：
文件里只记录「需要 12 字节，从 `0x401c` 开始」，真正的字节是加载时由内核补零的。

### 4.5 一张总表（建议收藏）

| 数据 | 存储位置 | 段类型 | 生命周期 | 符号字母 |
|---|---|---|---|---|
| 普通局部变量、形参 | 栈 | 运行时产生 | 出 `{}` | 无符号 |
| `malloc` / `new` | 堆 | 运行时产生 | 直到手动释放 | 无符号 |
| 全局变量（有初值） | 静态区 | `.data` | 进程全程 | `D` |
| 全局变量（无初值） | 静态区 | `.bss` | 进程全程 | `B` |
| `static` 全局（有/无初值） | 静态区 | `.data`/`.bss` | 进程全程 | `d`/`b` |
| `static` 局部（有/无初值） | 静态区 | `.data`/`.bss` | 进程全程 | `d`/`b` |
| `const` 全局 / 字符串字面量 | 只读区 | `.rodata` | 进程全程 | `R`/`r` |
| 函数代码 | 代码区 | `.text` | 进程全程 | `T`/`t` |

## 5. 问题五：静态区到底是什么

### 5.1 定义

> **静态区（静态存储区）是进程虚拟内存里专门存放「整个程序运行期间持续存在」的数据的区域。**
> 只要进程不退出，这块内存不会被自动回收，也不会随函数调用伸缩。

它和栈、堆是平级的三个独立区域。

### 5.2 静态区里到底有几个段

| 段 | 官方名 | 放什么 | 磁盘占用 | 权限 |
|---|---|---|---|---|
| `.data` | data segment | **有非零初值**的全局 / static 变量 | 占（PROGBITS） | 可读可写 |
| `.bss` | Block Started by Symbol | **没有显式初值**或初值为 0 的全局 / static 变量 | **几乎不占**（NOBITS） | 可读可写 |
| `.rodata` | read-only data | 字符串字面量、`const` 全局常量、虚函数表等 | 占 | **只读**，写入直接段错误 |

> 有些教材把 `.rodata` 单独拎出来叫「只读区」，有些直接归入静态区。**考试按教材，工程看 readelf**，两种说法都不算错，关键是知道 `.data` / `.bss` 是可写静态数据、`.rodata` 是只读静态数据。

### 5.3 `.bss` 为什么几乎不占文件空间？（一个经典面试题）

假设你写 `int big[1024*1024];`（4MB，全 0）：

- 如果放 `.data`，可执行文件就得**真的存 4MB 的 0**，毫无意义；
- 放 `.bss`，文件里只写「我需要 4MB 空间」，加载时内核/加载器分配 4MB 匿名页并清零（Linux 用 `mmap` 映射零页，还能写时复制）。

**结论：`.bss` 是「用运行时一次性清零，换磁盘和内存带宽」的设计。**

### 5.4 谁在静态区，谁不在

**在静态区：**
- 全局变量（不管有没有 `static`）
- `static` 全局变量
- **`static` 局部变量** ← 最反直觉的一个
- `static` 类成员变量（C++）
- 全局 `const` / 字符串字面量（在 `.rodata`）

**不在静态区：**
- 普通局部变量 → 栈
- `malloc` / `new` → 堆
- 函数机器码 → `.text`
- 类的**非静态**成员 → 跟着对象走（对象在哪它就在哪）

### 5.5 「静态」这个词的三重身份（超级易混，务必分清）

| 出现位置 | 例子 | 改变了什么 |
|---|---|---|
| 文件作用域的 `static` | `static int g;` | **链接属性**：外部 → 内部（名字只在本 .cpp 可见） |
| 函数内的 `static` | `void f(){ static int s; }` | **存储期**：自动 → 静态（生命周期变成进程全程） |
| 类成员的 `static` | `struct A { static int n; };` | 变量变成**全类共享一份**，不属于任何对象 |

同一关键字，三种语义，**没有统一含义**——这是 C 语言设计上被吐槽最多的地方之一。

### 5.6 静态区的三个特点（对比栈）

1. **分配时机早**：进程加载时就映射好，不是运行到代码才分配；
2. **大小固定**：编译期就确定，不会伸缩，也**不能**在运行中申请更多；
3. **地址稳定**：一次运行内地址不变（PIE + ASLR 只改基址，不改内部相对偏移），所以 `&g_init` 和 `&` 相邻变量之间差值恒定。

## 6. 问题六：块级作用域

### 6.1 定义

> **块级作用域 = 一对 `{ }` 围出的范围。**
> 它管两件事：**名字在这对花括号外不可见** + **块内的自动变量在这对花括号结束时失效**。
> 它**管不了**变量的存储区域（栈→静态区这种变化，只有 `static` 能做到）。

```c
{
    int x = 10;   // 块开始，x 诞生
}                 // 块结束，x 名字消失、生命周期结束
```

### 6.2 核心：作用域 vs 存储期是两条正交的轴

```
              存储期（内存在哪、活多久）
              ├── 自动（栈）──── 出块销毁
              └── 静态（静态区）── 进程全程

作用域（名字在哪可见）
              ├── 块级 ── 出 {} 看不见
              └── 文件/全局 ── 全文件可见（static 则限本文件）
```

四条组合都存在，其中**最容易误解的是第三条**：

| # | 作用域 | 存储期 | 例子 | 诡异之处 |
|---|---|---|---|---|
| ① | 块级 | 自动 | `void f(){ int a; }` | 正常，最常见 |
| ② | 全局 | 静态 | `int g;` | 正常 |
| ③ | **块级** | **静态** | `void f(){ static int s; }` | **名字出块就没，内存却活满全程** |
| ④ | 全局 | 静态但名字受限 | `static int g;` | 名字限本文件，内存一样活全程 |

### 6.3 块内 static：实测证据

```cpp
void f() {
    static int s_in_block = 100;
    {
        static int inner = 7;
        inner++;
        printf("inner=%d addr=%p\n", inner, (void*)&inner);
    }
    printf("s_in_block addr=%p\n", (void*)&s_in_block);
}
int main() { f(); f(); }
```

**实测输出**：

```
inner    =8 addr=0x55fde9926018
s_in_block addr=0x55fde9926014
inner    =9 addr=0x55fde9926018     ← 地址一模一样，值从 8 涨到 9
s_in_block addr=0x55fde9926014
```

两条结论：
- **地址两次完全相同** → 它不在栈上（栈地址会随帧变化），而在固定静态区；
- **值在累加（8 → 9）** → 出块并没有销毁它，只是**名字看不见了**。

**这就是「块级作用域」的全部含义：锁住名字，不锁住内存。**

> 顺带一条实测发现：`inner` 是块内的 static，出了内层 `}` 之后，在函数体里再写 `printf(..., &inner)` 会直接编译报错：
> ```
> error: 'inner' was not declared in this scope
> ```
> 作用域严格生效——这正是「名字」和「内存」分离的最佳演示。

### 6.4 嵌套块的销毁顺序

```cpp
void f() {
    A a("a");
    {
        A b("b");
    }              // b 先析构
}                  // a 后析构
```
**内层先死，外层后死**——栈式 LIFO。这个顺序是所有 RAII 的基础。

### 6.5 块级作用域的工程价值：RAII

```cpp
{
    std::lock_guard<std::mutex> lk(mtx);   // 构造即加锁
    // ... 临界区
}                                          // 出块，lk 析构，自动解锁
```

C++ 里「资源获取即初始化」之所以成立，完全依赖**块级作用域的确定性析构**：
不管中间 `return`、抛异常、`break`，只要离开 `{}`，析构必被调用。
Java / Python 没有这个保证（GC 不定时，`with` 靠语法），所以 C++ 的锁、文件句柄、智能指针敢这么写。

### 6.6 C 与 C++ 在块级作用域上的差别

| | C89 | C99 / C++ |
|---|---|---|
| 块内声明位置 | 必须在块开头 | 任意位置 |
| 块结束时有析构吗 | 无（没有析构概念） | 有，逆序析构 |
| 支持 `for(int i=...)` 的 i 只活在循环里 | ❌ | ✅（C99 起） |

## 7. 易错点总清单（20 条，按踩坑频率排序）

### 7.1 `static` 关键字（最高频）

| # | 错误认知 | 正确理解 |
|---|---|---|
| 1 | 「`static` 就是全局变量」 | `static` 有三种语义：文件域=改链接属性；函数内=改存储期；类内=全类共享。位置不同含义不同 |
| 2 | 「`static` 局部在 main 之前初始化」 | **错**。它在**第一次执行到定义行**才初始化（t1 的 `[static local] ctor` 在 `enter main` 之后打印，就是证据） |
| 3 | 「`static` 局部出函数就没了」 | 名字没了，**内存活满全程**（t3 里 `inner` 两次地址相同、值还累加） |
| 4 | 「`static` 变量存在栈上」 | 在**静态区**（`.data`/`.bss`），`nm` 显示 `d`/`b` 而非无符号 |
| 5 | 「全局 `static` 和局部 `static` 一样」 | 前者改**链接属性**（跨文件不可见），后者改**存储期**（生命周期变全程） |

### 7.2 初始化与默认值

| # | 错误认知 | 正确理解 |
|---|---|---|
| 6 | 「局部变量不初始化默认是 0」 | **是垃圾值**，读了就是 UB。只有静态存储期的才保证为 0 |
| 7 | 「全局变量初始化都要跑代码」 | 常量初值**编译期直接写进 `.data`**，运行时零指令 |
| 8 | 「跨文件全局对象初始化顺序无所谓」 | 顺序**标准不保证**，会出静态初始化顺序灾难。用函数内 static 规避 |
| 9 | 「`static int s = func();` 里 func 只跑一次」 → 这条是对的 | 但要注意：只有第一次进函数才跑，之后跳过（t2 实测 4 次 `run func` 里有 1 次是它） |
| 10 | 「`static` 局部初始化线程不安全」 | C++11 起**语言层面保证**只初始化一次（magic statics + guard 变量） |

### 7.3 生命周期与作用域

| # | 错误认知 | 正确理解 |
|---|---|---|
| 11 | 「出作用域内存就被清零」 | 只是栈指针回退，**内容原样还在**，读它是 UB 但常常真能读到旧值 |
| 12 | 「生命周期结束 = 内存被释放」 | 物理内存还在（栈帧复用、进程内静态区不动），只是**不再归你** |
| 13 | 「返回局部变量的地址能用」 | ❌ 悬垂指针，UB。函数返回后栈帧随时被覆盖 |
| 14 | 「`static` 局部活到 main 结束」 | 活到**进程结束**，main 返回后还有 `.fini_array` 那一程 |
| 15 | 「作用域 = 生命周期」 | 两个正交维度。块级 static 就是「作用域块级 + 存储期静态」的组合 |

### 7.4 存储位置

| # | 错误认知 | 正确理解 |
|---|---|---|
| 16 | 「全局变量在堆上」 | 在**静态区**；堆只给 `malloc`/`new` |
| 17 | 「`.bss` 是没分配内存」 | 是**不占磁盘空间**，内存照常分配并清零（`readelf` 显示 `NOBITS`） |
| 18 | 「字符串字面量可写」 | 在 `.rodata`，写入直接 **Segmentation fault** |
| 19 | 「`const` 局部变量在静态区」 | `const` 只约束**能不能改**，不改变存储期；`const int a;` 局部仍在栈上 |

### 7.5 程序入口

| # | 错误认知 | 正确理解 |
|---|---|---|
| 20 | 「main 是程序入口，全局变量在 main 里初始化」 | 真正入口是 `_start`/`_CRTStartup`；全局对象构造在 **main 之前**（`.init_array`），析构在 **main 之后**（`.fini_array`，逆序） |

## 9. 自测题（先答再看答案）

**Q1.** 下面编译能过吗？为什么？
```cpp
void foo() {}
foo();
int main() { return 0; }
```
<details><summary>答案</summary>
不能。全局域只允许声明/定义，不允许可执行语句。实测报错：`expected constructor, destructor, or type conversion before ';' token`。
</details>

**Q2.** `A global;` 的构造函数在什么时候执行？析构呢？
<details><summary>答案</summary>
构造：main 之前（CRT 遍历 `.init_array`）。析构：main 返回之后（遍历 `.fini_array`，且逆序）。两者之间内存一直在 `.data`/`.bss`。
</details>

**Q3.** 下面输出几行 `run func`？
```cpp
int func(){ puts("run func"); return 1; }
int g = func();
void t(){ int a = func(); static int s = func(); }
int main(){ t(); t(); }
```
<details><summary>答案</summary>
**4 行**（实测）。全局 g 一次 + 局部 a 两次 + static s 一次。
容易答成 3 行，就是漏算了「局部 a 每次进函数都要初始化」。
</details>

**Q4.** `static int s;` 在函数里，它的地址在栈上吗？怎么证明？
<details><summary>答案</summary>
不在栈。证明：多次调用打印 `&s` 地址恒定（实测 `0x55fde9926014` 两次一样），且 `nm` 显示 `d`/`b` 小写本地数据符号；栈地址是 `0x7ffe...` 区间且会随帧变化。
</details>

**Q5.** 为什么 `.bss` 段的 `size` 几乎为 0，但运行时确实有那么多内存？
<details><summary>答案</summary>
`.bss` 是 `NOBITS`，文件里只记录大小和起始地址，不存实际字节。加载时内核分配匿名页并清零（可映射共享零页，写时复制），所以省磁盘、省带宽。
</details>

**Q6.** 块内 `static` 变量出了 `}` 会怎样？
<details><summary>答案</summary>
**名字不可见**（再引用编译报错 `'inner' was not declared in this scope`），但**内存和值都保留**。作用域被限制，存储期不变。
</details>

**Q7.** 一个变量能否「作用域是块级，但生命周期是全程」？举例。
<details><summary>答案</summary>
能，就是块内的 `static` 变量。`void f(){ { static int x; } }`：名字只在内层块可见，内存全程有效。
</details>

**Q8.** `const int a = 5;` 放在函数里，它在哪个段？
<details><summary>答案</summary>
栈。`const` 只约束「不可改」，**不改变存储期**。只有全局/静态的 `const` 才进 `.rodata`。
</details>

## 11. 一句话记忆口诀（收尾）

**生命周期**
> 局部：块内活着，出块就死；全局和 static：开机到关机。

**存储位置**
> 栈是临时工，堆是你手动租的，静态区是程序一启动就占好、一直用到关门的固定工位。

**静态区**
> `.data` 有值，`.bss` 清零，`.rodata` 只读；文件里 `.bss` 不占地方，内存里它一分不少。

**块级作用域**
> `{}` 只管「名字能不能看见、栈变量什么时候死」；管不了 static——static 只是被关在块里，内存还在静态区活着。

**main 之外**
> 全局域写不了语句；你在 main 前后看到的执行，全是 `.init_array` / `.fini_array` 在替你跑构造和析构。
